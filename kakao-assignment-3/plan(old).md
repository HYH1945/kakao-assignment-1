# [2차 과제 기능 분석: 프론트엔드 vs 백엔드 역할 분리]

### 1. Todo CRUD 기능
- **프론트엔드 유지**: 텍스트 입력창 UI, 추가 버튼 클릭 이벤트, 인라인 수정 UI, 완료 시 취소선 등 시각적 화면 렌더링.
- **백엔드로 이관**: 고유 ID 생성(DB Auto Increment), 실제 데이터 생성/수정/삭제 로직 처리 및 영구 저장.

### 2. 상태별 필터링 기능
- **프론트엔드 유지**: '전체/진행 중/완료' 탭 UI 렌더링 및 클릭 시 URL 파라미터(`?filter=...`) 변경.
- **백엔드로 이관**: 기존 프론트엔드의 배열 `.filter()` 로직 완전 제거. FastAPI에서 쿼리 파라미터를 읽어 데이터베이스단에서 필터링 후 프론트에 반환.

### 3. 일간 뷰 및 주간 뷰 기능
- **프론트엔드 유지**: 화면 달력 UI, 이전/다음 날짜 및 주차 이동 버튼 렌더링.
- **백엔드로 이관**: 선택된 날짜에 해당하는 Todo 데이터만 추출하는 로직 (`?date=YYYY-MM-DD`). 주간 뷰의 날짜별 Todo 개수 집계 로직.

### 4. 로컬 스토리지 연동 
- **프론트엔드 폐기**: `localStorage.getItem / setItem` 및 `useEffect`를 통한 상태 동기화 로직 전부 삭제.
- **백엔드로 이관**: 데이터베이스(SQLite)가 모든 데이터의 영구 저장을 담당. 프론트는 상태를 브라우저에 저장하지 않고, 순수하게 백엔드와 API 통신(`fetch`)만 수행.



# [주요 기능 구현 명세 (과제 목표)]

### 1. Todo CRUD 기능
- 텍스트 입력창과 추가 버튼으로 새로운 Todo를 생성.
- 입력값이 비어있는 경우 Todo가 생성되지 않고 안내 메시지 표시.
- 생성된 Todo는 목록 형태로 화면에 표시되며, 각 항목은 수정/완료처리/삭제 가능.
- 완료 처리된 Todo는 텍스트에 취소선을 그어 시각적으로 구분.
- 기존 `prompt()` 대신, 인라인 입력창(항목 내 직접 텍스트 수정)으로 수정 UI 구현.

### 2. 상태별 필터링 기능
- 전체 / 진행 중 / 완료 필터 탭을 통해 원하는 Todo만 조회.
- 현재 선택된 필터 탭은 시각적으로 뚜렷하게 구분.
- 필터 상태는 URL 파라미터(`?filter=...`)로 관리하여 새로고침 시에도 유지.

### 3. 일간 뷰 및 주간 뷰 기능
- **일간 뷰**: 화면에 선택된 날짜(기본: 오늘)를 표시하고, 이전/다음 날짜로 이동. 선택된 날짜의 Todo만 목록에 표시. Todo 생성 시 현재 선택된 날짜 자동 저장.
- **주간 뷰**: 이번 주 날짜 목록 표시. 날짜 선택 시 해당 날짜 Todo 표시. 이전/다음 주차 넘기기 버튼 제공.
- 각 날짜 아래에 해당 날짜의 Todo 총 개수를 표시하고, '오늘' 날짜는 시각적으로 특별하게 강조.

### 4. Todo 검색 기능
- 검색창에 키워드를 입력하여 특정 Todo 내용을 검색.
- 필터 탭(진행 중/완료)과 검색 조건을 동시에 적용하여 조회 가능.
- 검색어 입력 시 불필요한 API 호출을 막기 위한 디바운싱(Debouncing) 적용.

  - `localhost:3000/todos/new`에 접속했을 때 생성 페이지가 보이는가
  - `"use client"` 선언이 필요한 컴포넌트와 필요하지 않은 컴포넌트를 구분할 수 있는가

## 5. API Route 작성하고 프론트-백 연동
- route.ts에 API Route 작성.
- action.ts에 Server Actions 작성하고 각 페이지에서 호출.
- **[생각포인트 - 데이터 통신 방식의 명확한 분리]**
  - **`route.ts` (API Proxy)**: 클라이언트(브라우저)에서 백엔드 실제 주소를 숨기고 CORS 이슈를 방지하기 위해 사용. 외부 HTTP 요청(`fetch('/api/todos')`)을 받아 FastAPI로 전달. 
  - **`actions.ts` (Server Actions)**: 페이지/컴포넌트에서 직접 호출하는 서버 함수(`import { createTodo } from '@/app/actions'`). 여기에 Server Action 작성하고 각 페이지에서 호출
- **적용 기준**: Todo 목록을 불러오는 등 서버 컴포넌트 내부의 로직은 `actions.ts`에서 FastAPI를 직접 호출하고, 클라이언트 컴포넌트(생성/수정 등)에서 통신할 때는 `route.ts`를 거쳐 FastAPI로 전달. 데이터 변경 후에는 `revalidatePath`로 즉각적인 캐시 갱신.
- **[테스트 포인트]**
  - Todo를 생성했을 때 FastAPI DB에 실제로 저장되는가
  - 목록 페이지에서 생성한 Todo가 바로 표시되는가
  - 수정, 삭제 후 목록이 올바르게 업데이트되는가
  - 브라우저 네트워크 탭에서 요청이 어떤 순서로 발생하는지 확인해봤는가

## 7. 서버 기반 상태별 필터링 구현
- 전체 / 진행 중 / 완료 필터 탭을 구현, 필터 상태를 ?filter=active, ?filter=completed 형태의 URL 파라미터로 관리
- FastAPI에 필터 조건을 쿼리 파라미터로 전달해 서버에서 필터링 (이때 필터링은 클라이언트(브라우저)가 아닌 FastAPI 서버에서 처리)
- 처리 과정 : ```python
클라이언트 → route.ts → FastAPI (/todos?filter=active) → DB 조회 → 필터링된 결과 반환```
- **[생각포인트 - useState vs URL 파라미터]**
  - 단순 클라이언트 메모리(`useState`) 기반 배열 필터링을 제거 (새로고침 시 초기화되는 문제 해결).
  - 대신 **URL 파라미터(`?filter=completed`)**와 `useSearchParams`를 사용하여 필터 상태를 주소창에 저장. 이를 통해 새로고침, 뒤로가기, 링크 공유 시에도 사용자의 탭 선택 상태가 완벽하게 유지됨.
  - 프론트에서 배열을 필터링하는 대신, Server Component(`app/page.tsx`)에서 URL 파라미터를 읽어 백엔드에 직접 필터링된 데이터를 요청(`GET /todos?filter=...`)하는 서버 주도형 필터링으로 구현.
- **[테스트 포인트]**
  - 필터 탭을 클릭했을 때 URL이 바뀌는가
  - URL을 직접 입력해도 해당 필터가 적용된 상태로 보이는가
  - 새 Todo를 추가했을 때 현재 필터가 유지되는가
  - 필터링이 클라이언트가 아닌 서버(FastAPI)에서 처리되고 있는가 (브라우저 네트워크 탭에서 확인)


## 8. 서버 기반 Todo 검색 기능 구현
- 프론트엔드가 아닌 백엔드(FastAPI)에서 DB를 직접 조회하여 검색 결과를 반환하도록 구현.
- 검색어를 ?search=키워드 형태의 URL 파라미터로 관리
- 키워드로 Todo 내용을 검색할 수 있는 검색창을 구현 (이 때 필터링과 검색을 동시에 적용할 수 있음, ?filter=active&search=키워드) 
- FastAPI에 검색 엔드포인트를 추가하고, 서버에서 키워드로 필터링
- GET	/todos?search=키워드 :	키워드로 Todo 검색
- GET	/todos?filter=active&search=키워드 :필터 + 검색 동시 적용
- 사용자가 검색창에 타이핑할 때마다 불필요한 API 요청이 쏟아지는 것을 방지하기 위해 **디바운싱(Debouncing)** 로직 적용.
- **[테스트 포인트]**
    - 검색어를 입력했을 때 URL이 바뀌는가
    - 검색 결과가 서버에서 필터링되어 오는가 (브라우저 네트워크 탭에서 확인)
    - 필터 탭과 검색을 동시에 사용했을 때 두 조건이 모두 적용되는가
    - 검색어가 없을 때 전체 목록이 다시 표시되는가

## 9. 서버 기반 일간/주간 뷰 연동 및 UI 구현
- 프론트엔드에 일간(오늘 날짜 기준) 및 주간 달력 UI 컴포넌트를 구현.
- 이전/다음 날짜(또는 주차) 이동 버튼 클릭 시, 선택된 날짜 상태를 `?date=YYYY-MM-DD` 형태의 URL 파라미터로 관리.
- 백엔드(FastAPI) `GET /todos` 엔드포인트에서 `date` 쿼리 파라미터를 받아, 해당 날짜에 생성/할당된 Todo만 필터링하여 반환.
- 주간 뷰 하단에 표시할 날짜별 Todo 개수를 집계하는 기능 추가 (백엔드에서 통계 데이터 반환 API 구현).
- **[테스트 포인트]**
  - 이전/다음 날짜 버튼 클릭 시 브라우저 URL(`?date=...`)이 올바르게 변경되는가?
  - URL 파라미터의 날짜를 수동으로 바꿨을 때, 해당 날짜의 Todo 목록만 정확히 서버에서 패칭되어 표시되는가?
  - Todo를 새로 생성했을 때, 현재 선택되어 있는 달력 날짜로 데이터베이스(`target_date` 등)에 정상 등록되는가?
  - 새로고침, 뒤로가기 시에도 사용자가 보고 있던 날짜 뷰 상태가 완벽하게 유지되는가?
